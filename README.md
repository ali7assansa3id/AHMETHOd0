# AHMETHOD — Smart Accounting & Business Management

نظام محاسبي متكامل، متعدد الشركات (Multi-tenant)، يعمل بالكامل داخل المتصفح
(Vanilla HTML/CSS/JavaScript) وجاهز للرفع على **GitHub Pages** بدون أي Backend.

هذا المشروع مبني فوق الملف الأصلي `COFFE-BATRA2026-9.html` (2900 سطر) دون حذف
أو استبدال أي وظيفة موجودة فيه — راجع قسم "الوظائف التي تم الحفاظ عليها" بالأسفل.

---

## 1) التشغيل

### محليًا
لا يمكن فتح `index.html` مباشرة بنقرتين على بعض المتصفحات بسبب سياسة CORS مع
ملفات JS المنفصلة. شغّل خادمًا محليًا بسيطًا من داخل مجلد المشروع:

```bash
python3 -m http.server 8080
# ثم افتح http://localhost:8080
```

أو بأي أداة مشابهة (`npx serve`, Live Server في VSCode... إلخ).

### GitHub Pages
ارفع محتوى هذا المجلد إلى مستودع GitHub، ثم فعّل GitHub Pages من إعدادات
المستودع (Branch: main, Folder: /root). كل المسارات نسبية (`./css/...`,
`./js/...`) ولا يعتمد المشروع على أي Backend أو PHP أو قاعدة بيانات خارجية.

### الحسابات الافتراضية
| الدور | اسم المستخدم | كلمة السر |
|---|---|---|
| المدير العام (Super Admin) | `admin` | `admin123` |

من شاشة الدخول: زر **"+ إنشاء حساب / شركة جديدة"** لتسجيل شركة جديدة (تحصل
تلقائيًا على مستخدم `company_admin` بصلاحيات كاملة داخل شركتها فقط).

### ملاحظة مهمة حول تقسيم الملفات (بخصوص قاعدة "الأولوية للحفاظ على الوظائف")

الملف الأصلي مبني حول **حالة عامة واحدة (`DB`)** وسجل عرض واحد (`RENDERERS`)
تتشارك فيه كل الأقسام (فاتورة المبيعات تستدعي `getItemStock` من المخازن،
التقارير تستدعي بيانات من كل الأقسام، القيود اليومية تُنشأ من كل مكان...).
تقسيم هذا الملف إلى `sales.js`/`purchases.js`/`inventory.js`/... منفصلة تمامًا
كان سيتطلب إعادة هيكلة عميقة (تمرير حالة، تحديد ترتيب تحميل دقيق لكل تبعية)
مع خطر حقيقي لكسر وظائف تعمل بشكل صحيح حاليًا — وهو بالضبط الخطر الذي طلبتَ
تجنّبه صراحة في التعليمات (القاعدة رقم 3 والقاعدة رقم 29).

لذلك: **بقي المحرك المحاسبي الأصلي كاملًا في `js/app.js` دون تقسيم شكلي**،
والتقسيم الفعلي الذي تم هو فصل الطبقة **الجديدة كليًا** وغير المرتبطة (تعدد
الشركات، الاشتراكات، تسجيل الدخول الموحّد) إلى ملفات مستقلة ومستقلة عن بعضها
فعليًا (`auth.js`, `companies.js`, `users.js`, `storage.js`, `permissions.js`,
`utils.js`). هذا يطابق تعليمة "الأولوية: الحفاظ على الوظائف > التقسيم المثالي
للملفات".

## 3) التعديلات التي تمت داخل `js/app.js` (كل تعديل، بلا زيادة)

هذه هي **فقط** الأسطر التي تم لمسها في الملف الأصلي (كل شيء آخر — آلاف
الأسطر — نُقل حرفيًا بدون أي تغيير):

1. `const STORAGE_KEY` → `let STORAGE_KEY` (لتصبح قابلة للتغيير لكل شركة).
2. `loadDB()` → `loadDB(companyId)`: إذا مُرِّر `companyId` يصبح المفتاح
   `acc_system_data_v1__<companyId>` بدلاً من المفتاح الثابت القديم — باقي
   الدالة (الإعدادات الافتراضية، الترقية، الهجرة) **كما هي حرفيًا**.
3. `doLogout()`: تمت إضافة سطر واحد فقط في النهاية لمسح جلسة المنصة أيضًا
   (نداء محمي `if(window.clearPlatformSession)`، لا يكسر شيئًا إن لم يوجد).
4. `buildNav()`: تمت إضافة اسم الشركة في `userBox` بجانب اسم المستخدم (تجميلي).
5. `saveUser()` / `deleteUser()`: تمت إضافة تحقق من تفرّد اسم المستخدم على
   مستوى المنصة كلها (بدل الشركة فقط)، ونداء محمي لتحديث الفهرس العام بعد
   الحفظ/الحذف.
6. تم حذف كتلة `DOMContentLoaded` الأصلية في نهاية الملف فقط (كانت تستدعي
   `loadDB()` بدون معرف شركة وتُظهر التطبيق مباشرة) — **هذا كان ضروريًا
   بالضرورة القصوى** لأن التشغيل الجديد يحتاج تحديد الشركة/الدور أولًا (عبر
   `js/auth.js`) قبل تحميل أي بيانات؛ تشغيل الكتلتين معًا كان سيكسر النظام.
   لم يتم حذف أي دالة — فقط كتلة "تشغيل تلقائي" واحدة تم نقل مسؤوليتها
   لملف `auth.js`.

لا تغيير آخر — لا حذف دوال، لا تغيير أسماء IDs/classes، لا تغيير تصميم.

## 4) الوظائف التي تمت إضافتها (طبقة جديدة بالكامل)

- شاشة دخول موحّدة لكل الأدوار الثلاثة (نفس تصميم الشاشة الأصلية).
- تسجيل شركة جديدة من شاشة الدخول (اسم الشركة، المدير، اسم المستخدم، كلمة
  المرور، الهاتف، البريد، نوع الاشتراك: تجريبي 14 يوم / أساسي 30 يوم /
  احترافي 365 يوم).
- حساب **Super Admin** (`admin`/`admin123`) لا يتبع أي شركة — له لوحة تحكم
  منفصلة لعرض/تفعيل/تعليق/تمديد/حذف الشركات والاشتراكات، وزر "دخول للبيانات"
  لعرض بيانات أي شركة (باستخدام حساب مديرها).
- عزل بيانات كامل بين الشركات (كل شركة في مفتاح `localStorage` مستقل تمامًا).
- بوابة اشتراك: عند انتهاء الاشتراك أو تعليقه، يُمنع الدخول وتظهر رسالة واضحة
  بتاريخ الانتهاء، مع فحص دوري كل 5 دقائق أثناء الاستخدام.
- حماية زر الرجوع في المتصفح (back/forward cache) — إعادة التحقق من الجلسة
  عند أي عودة للصفحة.
- ترحيل تلقائي وآمن لأي بيانات قديمة محفوظة بالمفتاح الأصلي (نسخة أحادية
  الشركة قبل هذا التحديث) إلى شركة باسم "الشركة الافتراضية" دون حذف أي بيانات
  قديمة (يتم *نسخ* المفتاح القديم لا نقله، فيبقى موجودًا حتى بعد الترحيل).

**ملاحظة عن نظام المستخدمين/الصلاحيات:** الملف الأصلي كان يحتوي بالفعل على
محرك صلاحيات كامل لكل قسم (`عرض/إضافة/تعديل/حذف`) وعلَم `isAdmin` وشاشة
"المستخدمون والصلاحيات" الجاهزة — لم يكن هناك حاجة لإعادة بنائه؛ تم فقط ربطه
بالأدوار الثلاثة المطلوبة: `company_admin` = `isAdmin:true`، `employee` =
`isAdmin:false` مع `perms{}` محددة، بالضبط كما كان يعمل أصلًا.

### القيود المعروفة (مذكورة بصراحة كما طلبت، وليست مخفاة)

1. **مكتبة Excel (SheetJS) لم تُختبر عمليًا.** بيئة التطوير التي بُني فيها هذا
   المشروع لا تملك اتصال إنترنت خارجي، فتعذّر تحميل المكتبة سواء من الرابط
   المحلي (`libs/xlsx.full.min.js` — غير موجود) أو من CDN (محجوب). هذا يظهر
   في الـ Console كخطأي 404 وهما السبب الوحيد لفشل فحص "لا أخطاء Console".
   **هذا ليس خطأً في الكود** — الكود يحاول التحميل المحلي أولًا ثم يتحول
   تلقائيًا لـ CDN عبر `onerror`؛ في متصفح فيه إنترنت فعلي (أو مع وضع ملف
   المكتبة الحقيقي داخل `libs/`) ستعمل دوال الاستيراد/التصدير كما كانت تعمل
   تمامًا في الملف الأصلي (لم يُمسّ كودها إطلاقًا).
   **يُنصح بشدة** أن يقوم المستخدم بتحميل `xlsx.full.min.js` من
   `https://cdnjs.cloudflare.com/ajax/libs/xlsx/0.18.5/xlsx.full.min.js`
   ووضعه في `libs/` قبل الرفع لـ GitHub Pages، ثم اختبار Excel فعليًا.
2. **الطباعة الفعلية (فتح نافذة طباعة المتصفح وفحص المخرج على الورق) لم
   تُختبر** — تم فقط التحقق آليًا أن دالة بناء HTML الخاصة بالطباعة تعمل
   بدون أخطاء. يُنصح باختبار الطباعة يدويًا من المتصفح قبل الاستخدام الفعلي.
3. **زر الرجوع في المتصفح (Back button)** تمت إضافة حماية له (`pageshow` +
   إعادة فحص الجلسة) لكن لم يُختبر آليًا بالضغط الفعلي على زر رجوع المتصفح؛
   الآلية تعتمد على معيار قياسي (`event.persisted`) وتُعيد فحص الجلسة، لكن
   يُنصح بتجربتها يدويًا.
4. لم يتم اختبار سيناريوهات الاستيراد من Excel لعملاء/موردين/أصناف فعليًا
   لنفس سبب عدم توفر المكتبة (البند 1).

## 6) كلمات المرور — ملاحظة أمنية مهمة

هذا إصدار **Front-End بالكامل يعمل على GitHub Pages بدون أي خادم**. كلمات
المرور (لكل من المدير العام والشركات والموظفين) **مخزّنة كنص واضح** داخل
`localStorage`، تمامًا كما كانت في الملف الأصلي (`DB.users[].password`).
لم يتم إضافة تشفير/Hashing لأن ذلك كان سيتطلب تعديل منطق تسجيل الدخول
والمقارنة في كل مكان بالملف الأصلي دون فائدة أمنية حقيقية — بما أن أي شخص
يملك حق الوصول لجهاز المستخدم أو لـ localStorage يمكنه قراءة البيانات على
أي حال (هذه طبيعة أي نظام Front-End بدون خادم حقيقي).

**هذا النظام مناسب للاستخدام الداخلي/التجريبي وليس بديلاً عن نظام مصادقة
حقيقي (Authentication Server) لبيانات حساسة عبر الإنترنت.**

## 7) ما لم يتم بناؤه (خارج النطاق، مذكور صراحة)

- Hashing حقيقي لكلمات المرور (انظر القسم 6).
- إشعارات فعلية (بريد/SMS) عند اقتراب انتهاء الاشتراك — يظهر فقط تنبيه داخل
  النظام والوحة إدارة الشركات.
- صلاحيات دقيقة على مستوى "تقرير واحد بعينه" (`reports.export`,
  `reports.print` كصلاحيات منفصلة) — التقارير حاليًا تتبع نفس نظام الصلاحيات
  الأصلي (قسم `reports` بالكامل مقصور على `isAdmin` فقط، كما كان في الملف
  الأصلي تمامًا).
